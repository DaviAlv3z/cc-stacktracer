# AdonisJS integration

How to instrument an AdonisJS 6 or 7 application with the cc-stacktracer SDK: the HTTP middleware, the
exception handler, the user and the customer (subtenant) on spans, and database instrumentation through
Lucid/Knex. The basics require SDK 3.2 or later; identity on spans, SQL on database spans and the driver's
error fields require 3.4.

> Up to 3.1 the official middleware emitted nothing in a real Adonis app: it called
> `ctx.response.getResponse()`, which Adonis does not have. If you wrote your own middleware because of
> that, 3.2 lets you replace it with the official one.

## Where to initialize

In a dedicated preload, `start/stacktrace.ts`, registered **first** in `preloads` in `adonisrc.ts`, before `#start/routes` and `#start/kernel`. It is a single initialization, through `auto`. It also turns on Lucid and, when Adonis shuts down (the deploy's SIGTERM), sends whatever is still queued:

```ts
// start/stacktrace.ts
import app from '@adonisjs/core/services/app'
import db from '@adonisjs/lucid/services/db'
import { StackTrace } from 'cc-stacktracer'

await StackTrace.auto({
  apiKey: process.env.STACKTRACE_API_KEY!,
  serviceId: process.env.STACKTRACE_SERVICE_ID!,
  endpoint: process.env.STACKTRACE_ENDPOINT!,
  release: process.env.APP_VERSION,
  enableGlobalHandlers: true,
  // 3.4: the scope's user.id and subtenant (setUser / setTags) on spans, the root span included.
  identityOnSpans: true,
  lucid: db,
  // 3.4: the SQL with placeholders in db_statement, the bindings masked in db_parameters.
  lucidOptions: { statement: true, parameters: 'masked' },
})

// SIGTERM (deploy, `docker stop`): Adonis shuts the app down and the SDK sends what is still queued.
app.terminating(async () => {
  await StackTrace.shutdown()
})
```

```ts
// adonisrc.ts
preloads: [
  { file: () => import('#start/stacktrace'), environment: ['web', 'console'] },
  () => import('#start/routes'),
  () => import('#start/kernel'),
],
```

`console` is for jobs and `node ace ...` commands (see "Jobs and commands"); leave the `test` environment out,
so test telemetry does not reach the dashboard. Do not call `init` and then `auto`: the second call replaces the
first one's client. This is the setup the consumer smoke runs in an app generated by `create-adonisjs`
(Adonis 6 and 7).

## HTTP middleware

Register the SDK middleware as **server middleware**, in `start/kernel.ts`, before everything that handles the
request — but **after** the middleware that answers on its own, without reaching the router:

```ts
server.use([
  () => import('#middleware/container_bindings_middleware'),
  () => import('@adonisjs/static/static_middleware'), // if present
  () => import('@adonisjs/cors/cors_middleware'), // answers the OPTIONS preflight without calling next()
  () => import('cc-stacktracer/adonis/middleware'),
  // ...the rest
]);
```

It must be server middleware, not route middleware: server middleware runs before routing. That way:

- 404s, session failures and CSRF failures are traced too;
- the root span carries the route pattern (`/users/:id`), read after the match;
- a request that matched no route (404, a bot probing `/.env`) goes into a single bucket, `[unmatched]`,
  instead of becoming one route row per URL. The path, with ids masked, is kept in the span attribute
  `url.path`.

A static file and a CORS preflight match no route: with the SDK **in front of** static and CORS, each one becomes
an `[unmatched]`. That is why they come first. To sample bot scanning, create in the dashboard, under the
service's **Capture** page, the rule `eventType: http`, `endpoint: [unmatched]`, `sampleRate: 0.05` (requires
`capturePolicyRefreshMs` in `init`).

Each request runs inside an `AsyncLocalStorage` holding the HTTP snapshot, and logs, errors and child spans
inherit the trace, the method and the route. The root span carries the request identity: `http.request_id` (the
`X-Request-Id` Adonis generates with `generateRequestId: true`), `user_agent.original`, `host.name`,
`process.pid`, `telemetry.sdk.version` and, with `init({ clientIp })`, `client.address`.

To instrument only some routes, the function form works as route middleware:

```ts
import { stacktraceAdonisMiddleware } from 'cc-stacktracer/adonis';

router.get('/reports/:id', [ReportsController, 'show']).use(stacktraceAdonisMiddleware());
```

Do not register both (server and route) for the same request: that is two root spans.

## User and customer (subtenant)

After authentication, mark the user and — in an application that serves several customers — the customer:

```ts
// app/middleware/auth_middleware.ts
import { StackTrace } from 'cc-stacktracer'

export default class AuthMiddleware {
  async handle(ctx: HttpContext, next: NextFn, options: { guards?: (keyof Authenticators)[] } = {}) {
    await ctx.auth.authenticateUsing(options.guards)
    StackTrace.setUser({ id: String(ctx.auth.user!.id) })
    StackTrace.setTags({ subtenant: tenant.slug }) // the customer's slug; where it comes from is up to your app
    return next()
  }
}
```

- **Events** (logs and errors) of the request carry `metadata.user.id` and `tags.subtenant`.
- **Spans**, with `init({ identityOnSpans: true })` (3.4): the request's root span — read when it ends — and every
  span started after the marking (database, outbound calls, `withSpan`) carry `user.id` and `subtenant`. Every
  authenticated trace then shows up in the subtenant filter of the traces screen. The auth's own queries run
  before the marking and do not carry them.
- The scope belongs to the request: one request's user never shows up in another.
- Use the user's internal id — never an e-mail, a national id or a name — and a readable, stable slug for the
  customer (`0042-prefeitura-de-peruibe`), never an id. See the [subtenant guide](./subtenant.en-US.md).

For other root span attributes (the customer's plan, a feature flag), call
`StackTrace.setRootSpanAttributes({ 'customer.plan': 'premium' })` from anywhere in the request.

## Exception handler: `recordRequestError`

The Adonis exception handler handles the exception **inside** the middleware's `next()`. The SDK middleware
never sees the exception: to it, the request just ended with a status. So call
`StackTrace.recordRequestError` in the handler's `report()`:

```ts
// app/exceptions/handler.ts
import { ExceptionHandler, type HttpContext } from '@adonisjs/core/http';
import { StackTrace } from 'cc-stacktracer';

export default class HttpExceptionHandler extends ExceptionHandler {
  async report(error: unknown, ctx: HttpContext) {
    StackTrace.recordRequestError(error);
    return super.report(error, ctx);
  }
}
```

The response decides what happens:

- **5xx** (default `500-599`, configurable through `httpServerErrorStatuses`): ONE error event, with the final
  status and the route, linked to the root span. The root span carries `error_type` and `error_message`.
- **4xx** (validation, 404, 403): nothing. An exception that turns into a 4xx is not an application error.

Without that line, a 5xx goes out with the root span marked as an error, but with no event, no stack and no
`error_type`.

In 3.4 the event carries the error's fields on its own: for a database error, `db.error.kind`, `db.error.code`
(SQLSTATE `23505`, `ER_DUP_ENTRY`…), `db.error.constraint` and the like; for an Adonis error, `error.code`
(`E_ROW_NOT_FOUND`). There is no need to copy them into tags in `report()`.

Do not call `captureException` in `report()`: it sends right away, before there is a status — a 404 or a 422
would become an event. `recordRequestError` follows Error Tracking: with `init({ errorTracking: false })`, only
the root span gets the exception, and no event is sent. Outside a request, it sends the error right away, like
`captureException`.

`captureException` is still the right call for errors the app handles without rethrowing. Calling both on the
same error object produces a single event.

An exception recorded on a span — a failed query, for instance — becomes an event even if the app catches it and
answers 409: in the Error Tracking model, the span's error is the request's error. If the app uses constraint
violations as control flow, validate first (VineJS `unique`/`exists`).

## Custom middleware with `startHttpRequest`

If you need a middleware of your own, open the request before routing and pass the route as a **function**. It
is read when each event is sent and when the root span closes.

```ts
import { startHttpRequest } from 'cc-stacktracer/generic-http';

const trace = startHttpRequest({
  method: ctx.request.method(),
  url: ctx.request.url(true),
  headers: ctx.request.headers(),
  route: () => ctx.route?.pattern,
});
```

Do not write to internal fields of the returned object: they may change in any version. To set the route later,
use `trace.setRoute(pattern)`.

## Database (Lucid / Knex)

The `lucid: db` in the preload above instruments every Lucid connection, including the ones opened after boot
(and the ones created per tenant at runtime), with `db_system` taken from the driver: `pg` → `postgres`,
`mysql2` → `mysql`, `mssql` → `sqlserver`, `better-sqlite3` → `sqlite`. It works from Lucid 20 to 22. Each query
is a `db` span, with:

| Attribute | Content | Since |
|---|---|---|
| `db_system`, `db_operation`, `db_table` | engine, verb and table | 3.3 |
| `db.namespace`, `db.connection` | the database and the Lucid connection name | 3.4 |
| `db_statement` | the SQL with **placeholders** (`$1`, `?`), up to 4,000 characters — with `lucidOptions.statement` | 3.4 |
| `db_parameters` | the bindings, masked — with `lucidOptions.parameters` | 3.4 |
| `db.error.*` | on a failed query: `kind`, `code`, `constraint`, `table`, `sqlstate`, `errno`… | 3.4 |

`parameters: 'masked'` keeps numbers, booleans, `null` and UUIDs and replaces text with `[string:<length>]` and
dates with `[date]`. If the schema stores a national id or a phone number as a number, use `parameters: 'types'`,
which masks numbers too. `lucidOptions.attributes: () => ({ ... })` adds attributes to every database span, read
when the query starts. None of the three is on by default.

### Configure knex on each connection

```ts
// config/database.ts
/**
 * For knex: `compileSqlOnError: false` puts the SQL with PLACEHOLDERS (not the values) in the error message;
 * `asyncStackTraces` makes the error's stack point at the app line that ran the query.
 * `compileSqlOnError` is not in Lucid's type, hence the separate object.
 */
const knexErrorOptions: Record<string, unknown> = { compileSqlOnError: false }

// on each connection:
  asyncStackTraces: true,
  ...knexErrorOptions,
```

- By default knex prefixes the error message with the SQL **with the values**: on MySQL and SQLite a duplicate
  insert becomes `insert ... values ('someone@x.com') - Duplicate entry ...`, and that message goes to your log and
  to the event. With `compileSqlOnError: false` it reads `values (?)`. On PostgreSQL nothing changes (the SQL
  already has `$1`), but keep it uniform.
- Without `asyncStackTraces`, a `pg` error's stack has only the driver parser's frames — no line of your app. The
  cost is one `new Error()` per query built.
- MySQL and SQL Server put the duplicate **value** in the driver's own message (`Duplicate entry 'someone@x.com'
  for key ...`), with or without `compileSqlOnError`. On events, redact it with `beforeSend`; the database span's
  `error_message` keeps the driver's message.

### Do not measure the same query twice

**Do not wrap a Lucid query in `StackTrace.runQuery`** or in `measure({ kind: 'db' })`: with the plugin on, that
creates a second `db` span for the same query, and the dashboard counts it twice in the bottlenecks. To give a
group of queries a business name, use a business span — the queries become its children:

```ts
import { StackTrace } from 'cc-stacktracer';

const report = await StackTrace.withSpan(
  'report.monthly',
  () => Report.query().where('period', period),
  { type: 'business' },
);
```

`runQuery` is for databases **outside** Lucid — a `pg` or `mssql` pool of your own.

Without `auto`: `StackTrace.register(createLucidStackTracePlugin(db, { statement: true, parameters: 'masked' }))`
(from `cc-stacktracer/db-lucid`), before or after `init`.

## Jobs and commands

A job, cron, queue consumer or ace command has no request: open the trace with `withTrace`.

```ts
import { StackTrace } from 'cc-stacktracer';

await StackTrace.withTrace('job.process-batch', async () => {
  StackTrace.setTags({ subtenant: customer.slug });
  await processBatch(customer);
});
```

In 3.4 `withTrace` opens a scope of its own: the job's `setUser`/`setTags` apply to it alone. **Outside** a
request or a `withTrace`, `setUser` and `setTags` write to the whole process's scope — never mark a user or a
customer there. A job that ends naturally delivers its telemetry on its own; before `process.exit()`, call
`await StackTrace.shutdown()`.

## Business context

Wrap domain operations with `withBusinessContextAsync` so the entity and the operation show up on every event
emitted inside the callback.

```ts
await StackTrace.withBusinessContextAsync({ entity: 'order', operation: 'approve' }, async () => {
  StackTrace.log('order approved', { orderId });
});
```
